# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## What this is

**Voicent Onboarding** is Jay's internal client onboarding app, in the style of Launchpad. Jay creates a client, picks a template, and sends the client a magic link. The client works through steps (forms, uploads, connect an integration, book a call, approve a deliverable, tasks) and Jay watches progress. Each onboarding mirrors into the AIOS app as a project with tasks.

One data-driven engine serves a plumber (one question per screen, on a phone) through an agency or MSP (full checklist, several contacts, approvals). The difference lives in the template, never in code.

Plan and rationale: `plans/2026-11-06-client-onboarding-app.md` in the `jaypasz/voicent-aios` workspace repo. It is the source of truth for scope and phases.

## State

Phases 1 to 4 done: scaffold, data model, migrations with row level security, auth, the template schema and YAML loader, four presets, the six v1 step types, services and the admin API (clients, templates, onboardings, steps, comments), `python -m app.cli seed`, the magic-link client portal API (`/api/portal`: exchange, session, view, answer, comment, upload URL), admin link controls, and file uploads to a private Supabase Storage bucket. The client portal UI (focus and checklist layouts, one renderer per step type) and the admin app (onboardings, clients and contacts, templates with YAML import, onboarding detail with answers, files, comments and link controls, new onboarding). Reminders for clients who go quiet (text through Twilio, email through Resend; never at night, a capped number of times, a flag for Jay when they give up) and a one-way sync of each onboarding into the AIOS board (one project, one task per step), both run by a timer inside the web process. The Voicent-App provisioning hook (Step 11): a signed webhook when an onboarding whose template has `on_complete: provision_voicent_workspace` is finished, off until its two settings are set, with its receiving contract in `ARCHITECTURE.md`. The step builder: drag-and-drop step cards with an add menu on the right, used to build and edit templates (`/templates/new`, `/templates/:id/edit`), to customise a client's copy when creating an onboarding, and to edit a draft's steps (`/onboardings/:id/steps`), with "save as template" from either; and a collapsible left menu. Tenancy and branding that follow Voicent-App: one org per Voicent tenant (direct or reseller), people sign in with their Voicent-App account and bring their role, superusers pick any org, and each org's brand (logo and colours from Voicent-App; name and senders set here) is used in the portal, the admin app and reminders. A workspace is requested only for paying clients (contract version 2: tenant, files as links, no connected accounts). Onboarding pages have tabs (Overview, Steps, Client preview, Links & follow-up). The team: a linked org's whole team comes from Voicent-App, other orgs invite by email; an owner per onboarding (whoever made it, by default) and a team member per step; in-app notifications with an unread count, also emailed if the person wants. The pipeline and tasks: each client has a stage (lead, onboarding, won, lost, stalled) shown on the Clients page with a filter, and the team has tasks (a Tasks page, and a panel on each client). Stages: an onboarding's sections are stages that the team signs off before the next opens to the client, shown grouped in the builder, the admin overview (with a stage tracker and a sign-off button) and the portal; each step has a start and due day picked on a calendar. When a sign-off opens a stage with client work, the client gets one message about it. Not built yet: the receiving endpoint in Voicent-App (separate work in that repo). **Not verified against the real services: Twilio, Resend, the AIOS app, Voicent-App (its directory and its receiving endpoint), Supabase login, uploads to Supabase Storage. All of those were tested against fakes of their APIs.**

## Layout

Virtualenv in `backend/.venv`.
- `frontend/` — Vite 8 + React 19 + TypeScript 6, linted with oxlint, tested with Vitest. Own `package.json`. `src/api` (fetch client, types, TanStack Query hooks), `src/auth` (optional Supabase login), `src/portal` (the client's pages: `session.tsx`, `FocusLayout`, `ChecklistLayout`, `StepPanel`, `steps/` one renderer per type), `src/admin` (Jay's pages), `src/builder` (the step builder: `doc.ts` document model, `StepsBuilder.tsx`, `ConfigEditor.tsx` one settings panel per step type, `SaveAsTemplate.tsx`), `src/components`, `src/lib`.
- One Railway service builds the `Dockerfile`: the SPA is served by FastAPI next to `/api`.

## Commands

Backend (from `backend/`):

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env                      # APP_ENV=local AUTH_DISABLED=1 for local work
uvicorn app.main:create_app --factory --reload   # http://localhost:8000, Swagger at /api/swagger (APP_ENV=local only)
python -m pytest -q
python -m app.cli nudge --dry-run     # who would be reminded right now; sends nothing
python -m app.cli sync                # one AIOS sync pass
python -m app.cli provision --dry-run # which Voicent workspace requests are due; sends nothing
python -m app.cli seed --org-name Voicent --org-slug voicent --admin-user-id <supabase user id> --admin-email <email>   # first org, first admin, preset templates
TEST_POSTGRES_URL=postgresql://... python -m pytest -q tests/test_migrations.py   # also checks RLS on a real Postgres
alembic upgrade head
alembic revision --autogenerate -m "what changed"   # then review it; a test fails if models and migrations disagree
```

Frontend (from `frontend/`): `npm install`, `npm run dev` (proxies `/api` to :8000), `npm run lint`, `npm test`, `npm run build`.

## Rules

- **Auth fails closed.** Every `/api` route except `/api/health` needs a Supabase user JWT (admin) or a `SERVICE_TOKENS` entry. `AUTH_DISABLED=1` only works with `APP_ENV=local`; otherwise the app refuses to start.
- **Two audiences, two door sets.** Admin routes live under `/api` and need admin auth. Client routes live under `/api/portal` and need a session token that came from a magic link, scoped to one onboarding and one contact. A portal route must never read outside that scope.
- **Nothing on `/api/portal` takes an onboarding id.** Which onboarding and contact is decided by the session token alone, and `deps.portal_ctx` re-checks the link row on every request, so revoking a link cuts off its sessions at once. Every failure is the same 401 (`portal.UNAVAILABLE`); a step that doesn't exist and one a client may not see are the same 404.
- **Rate limits.** Exchange: per client address and across everyone. Writes: per link. The client address comes from `X-Forwarded-For` and can be spoofed, which is why the global limit and the per-link limit exist. In-process, so per instance: move to Redis if this ever scales out.
- **Internal steps never reach the portal.** A step with `visibility = internal` must not appear in any portal response, comment thread or sync payload visible to a client. A test must prove it.
- **Routers stay thin; `services.py` holds the rules.** Every service function takes `org_id` and filters by it. A row from another org is `NotFound`, never a leak (`tests/test_api.py` proves it with two orgs). Admin requests resolve their org in `deps.current_org` (a person's `org_members` row; `X-Org-Id` for service tokens when there are several orgs).
- **A client's steps can be customised, before and after sending (not once archived).** `POST /onboardings` takes optional `sections`/`steps` that replace the template's in this onboarding's own copy (validated exactly like a template; name, slug, layout and `on_complete` stay the template's). `PUT /onboardings/{id}/document` edits them at any time; a step that already holds answers, files or comments can't be removed or change type (409 listing each; skip it instead). `GET /document` returns an `etag`; send it back and a save made from a stale screen is refused (409). After sending: new steps get due dates counted from `started_at`; a finished onboarding that gains an open step is active again, and an active one with nothing left open is finished (`_reconcile_status`; a Voicent-App delivery already made is never repeated); editing is not client activity, so the quiet-client timer is untouched; the AIOS sync renames a step's task and closes the task of a removed step. A done step whose settings change is re-checked against its latest answer (`_recheck_answer`).
- **A new step type is one file in `app/steps/` plus an entry in `registry.py`.** It declares its config schema, validates and cleans responses (redacting free text), and says what status an accepted answer leaves the step in. Declared-but-unbuilt types (`credential_share`, `info_video`, `payment_link`) are refused in templates until they are built.
- **Always `Depends(get_db, scope="function")`, never plain `Depends(get_db)`.** The commit then happens when the handler returns, before the response and before any background task. With the default scope a background task (the AIOS sync) runs while the request's changes are still uncommitted and reads stale data. The in-memory test database hides this (all its sessions share one connection), so `tests/test_aios_sync.py` pins it on a file database.
- **Background jobs run inside the web process, so run one instance.** Reminders stay safe if it is ever scaled out (a unique constraint on (onboarding, contact, channel, round) refuses a second send) and so does the sync (it reconciles), but the work would repeat. `Settings.jobs_enabled` is False in code and on by default from the environment, so tests never start a thread.
- **Reminders (`nudges.py`).** Stalled means active, not paused, client steps left, and quiet for the template's `nudge_after_days`. One channel per contact: a text only with recorded consent, otherwise email. Texts and automatic emails never go out between 21:00 and 08:00 in the client's own time zone (`Client.timezone`); a manual reminder skips the email rule but never the texting rule. At most `NUDGE_MAX` automatic rounds, then `Onboarding.attention` is set for Jay; a client acting clears it. Every reminder gets a fresh magic link (links are stored only as hashes) and a link for a failed send is revoked. Provider error text is never shown; the one thing read from Twilio's answer is the numeric code for "this number replied STOP", which withdraws consent. Time is passed in (`now=`, `app.state.clock`) so tests never depend on the clock.
- **Telling the client about edits (`changes.py`) is batched and quiet.** An admin edit of a sent onboarding (unless saved with `notify_client: false`) sets `steps_changed_at` and remembers what the client's steps looked like (`client_seen_steps`, client-visible steps only: key, title, fingerprint). When it has sat unedited for `CHANGE_NOTICE_DELAY_MINUTES` (10) the next job pass sends ONE message per contact with open steps listing what is new, updated, no longer needed or reordered, compared with what they last saw; edits that cancel out send nothing. Same rules as reminders: text only with recorded consent, never at night where the client is (the notice waits), fresh magic link per contact (revoked if the send failed), STOP withdraws consent. Claimed with one conditional UPDATE so it goes once; a failed send isn't retried. Internal steps, answers and comments never appear in it. It runs only while the onboarding is active (a paused one keeps it pending).
- **AIOS sync (`aios_sync.py`) is one-way and reconciles.** Project id `onb-<onboarding id>` (creating it twice is harmless), one task per step, found again by its `link` if a reply was lost. IDs are saved after every call. Creating a task and adding a comment are attempted once (a retry could duplicate); reads and updates are retried with backoff. `sync_version` goes up on every change and `synced_version` moves only to the version a pass actually read, so a change that lands mid-sync is never lost. **Only titles, statuses, dates and one-line summaries go out, through `redact()`; never a form answer, a file, a client comment or a link token.** A test checks the raw requests for exactly that.
- **Tenancy follows Voicent-App.** One org per Voicent tenant (`direct` or `reseller`). `deps.current_org` asks `tenancy.access_for`, which reads Voicent-App's directory (read only, cached 5 minutes) and copies the membership and role (`admin`, `manager`, `member`, `viewer`; unknown is `viewer`) with `source = "voicent"`, removing it when Voicent-App does. `seed` memberships (`source = "local"`) are never touched. A viewer gets 403 on any write; `AdminOrg` guards admin-only settings; a Voicent superuser may act in any org via `X-Org-Id`. If the directory is down, the last copy is used and a new person waits. With `VOICENT_SUPABASE_*` unset, nothing changes.
- **The team (`routers/team.py`).** A linked org's people are copied from Voicent-App's tenant (`tenancy.sync_team`, on the Team page) so they can be assigned before they sign in; people and roles change only there (409 here). Other orgs invite by email (`org_invites`); an invite is accepted when someone signs in with that address (`tenancy.accept_invites`). The last admin can't be removed or demoted. An onboarding has an owner (`owner_member_id`, the maker by default) and each step a team follower (`team_assignee_id`, never shown to clients). Assigning someone from another org is a 404. `request.state.member_id` is the caller's own membership; `SelfOrg` lets a viewer change only their own things (notification preference, marking read).
- **Notifications (`notifications.py`) are our own wording, never what a client typed.** Who hears what: a new owner or step follower (never for your own action), the step follower (else the owner) when a client answers, the owner when it finishes or the client goes quiet after every reminder. Shown in the app; emailed if the person wants (`notify_email`) and email is set up. Each email is claimed with one conditional UPDATE so it goes once; news older than a day is never emailed late.
- **A reseller's clients never see "Voicent".** Every client-facing name comes from `branding.display_name` (the org's brand name, else a reseller's own name). Brand fields are checked by `branding.clean` whatever their source (https logo, `#rrggbb`). Logo and colours of a linked org come only from Voicent-App (409 if changed here). Emails keep our verified address and change only the name.
- **Voicent provisioning (`provision.py`) sends once, is signed, and only for paying clients.** It fires only when an onboarding is completed **and** its client is marked paying (`clients.paying_since`), in either order, and its own snapshot says `on_complete: provision_voicent_workspace`, and only when `VOICENT_PROVISION_URL` (https) and `VOICENT_PROVISION_SECRET` (32+ chars) are set. Finishing queues a delivery in the database; one conditional `UPDATE` claims it (with a lease, so a crash is retried), so it goes out once. Timeouts, 408, 429 and 5xx retry with backoff under the same `delivery_id`; any other 4xx stops and waits for Jay; "send again" makes a new `delivery_id`. Signature: `v1=` hex HMAC-SHA256 of `<timestamp>.<body>`. **Only the tenant, org, client, contacts, client form answers (redacted again) and the client's uploaded files as one-hour signed links go out; never file contents, comments, approvals, connected-account details, internal steps or link tokens.** Leads (finished but not paying) never reach Voicent-App. Tests check the raw request for exactly that. The contract in `ARCHITECTURE.md` is what Voicent-App builds against: change both together, and bump `schema_version` for anything a receiver must handle.
- **A client's stage is worked out, not stored (`Client.stage`).** Lost or stalled when Jay set `clients.outcome`, else won once `paying_since` is set, else onboarding while one of their onboardings is active or paused, else lead (a draft or finished-but-unpaid onboarding is still a lead). Only `outcome` is stored, and a paying client can't be given one (409). There is no funnel or lead capture here: leads and GTM live in other tools.
- **Two kinds of team work, kept apart.** A `task` step (`steps/task.py`) is part of an onboarding's flow, for the client or the team by `config.audience`; the audience sets `visibility` through `StepType.visibility_for`, and it can't change once the step holds an answer or comment. Team task steps are listed on the Tasks page by `GET /api/tasks/in-onboardings`. A `tasks` row (`routers/tasks.py`) is a standalone to-do about a client ("chase the invoice") with an assignee and due date, never tied to an onboarding. Neither kind of team work reaches a portal response, the AIOS comments or the Voicent-App payload. A client or assignee from another org is a 404; finishing twice keeps the first time; free text is redacted on write.
- **Stages (`stages.py`).** A template's `sections` are stages, in their listed order. A section needs a sign-off unless it says `signoff: false`; until it has one (`stage_signoffs`, by an org admin or manager, only once every step in it is done or skipped), every later stage is locked: the client sees its steps but can't answer them (409), reminders leave them out, and the onboarding can't finish. Our team may work ahead in a locked stage. Steps outside a section are never locked. Withdrawing a sign-off relocks what follows (not once finished). Steps are listed in stage order. The portal's stage state is worked out from the client's own steps only (`waiting` = theirs are done, it waits on us), so it never hints at internal ones. Migration 0011 marked the sections of onboardings already sent as `signoff: false`, so nobody was locked out mid-way.
- **Stage-opened notice (`stage_notices.py`).** A sign-off that opens a stage with open client steps queues a notice (`stage_opened_at`, `stage_opened_keys`); withdrawing the sign-off first takes back what locked again. After the change-notice quiet period, each contact with steps of their own in the opened stages gets one message naming the stage (email also lists their steps), sent through `changes.tell` under the reminder rules (consent, never at night, fresh link, a failed send's link revoked, STOP withdraws consent), claimed with one conditional UPDATE. Never an internal step or a stage with nothing for them. Active onboardings only; a paused one waits.
- **Step dates.** `PUT /onboardings/{id}/steps/{key}/schedule` takes `start_on` and `due_on` as calendar days; the due day is stored as `due_at`, the end of that day in the client's time zone, and returned as `due_on` in the client's zone (show that, not a browser conversion of `due_at`). Sending keeps a date picked on a draft and fills the rest from `due_offset_days`.
- **Migrations on SQLite** run with foreign keys off (`alembic/env.py`), because SQLite rebuilds a table to alter it and would otherwise cascade-delete child rows. Postgres alters in place.
- **Every row has `org_id`**, and every query filters by it. Row level security is on with no policies, so the Supabase Data API sees nothing; the backend connects as the table owner and enforces org and onboarding scope in code.
- **Magic link tokens are stored only as a hash.** The raw token exists once, when issued. Expired, revoked and unknown links all answer the same way.
- **Templates are versioned JSON in the database** (`template_versions`). YAML is import and export only. An onboarding copies its template version into its own snapshot, so editing a template never changes a live client's flow.
- **Free text is redacted on write** (`app/redact.py`) and again before anything is synced out.
- **Credentials are never collected in v1.** `connect` steps record a status and an account label, never a token. A future `credential_share` step uses Fernet encryption with a one-time reveal and no export or sync path.
- **An optional feature's settings must never stop the app starting.** A half-set variable (uploads, SMS, email, AIOS sync) turns that feature off and logs a warning (`Settings.optional_warnings`). Only settings the whole app depends on (auth, database) are fatal in `validate()`. A variable that exists for another purpose (`VITE_SUPABASE_URL`) must not be read as a signal for an unrelated feature.
- **Provider error text is never passed on.** Messages are our own wording plus a status code.
- **Models and migrations must agree.** Change `models.py`, generate a migration, keep `tests/test_migrations.py` green. Migrations must also run on Postgres.
- **Rate limits are real.** The portal's exchange and write endpoints are enforced, not declared.

## Frontend rules

- **Two apps in one bundle.** `/c/:token` is the client portal and never touches Supabase or admin auth. Everything else is the admin app behind `AuthProvider`. Without `VITE_SUPABASE_*` the admin app runs in local mode (no login), which only works against a backend started with `APP_ENV=local AUTH_DISABLED=1`.
- **The portal session lives in memory only.** The link token in the URL is exchanged once for a short-lived session (`portal/session.tsx`), renewed before it expires, and retried once on a 401. A 401 or any failed exchange shows the same "This link isn't available" page and never says why. `index.html` sets `referrer: no-referrer` and `noindex` because the address of a client page is their key.
- **Brand is applied as CSS variables on a container** (`lib/brand.ts`: `brandStyle`, readable text colour by contrast; `safeLogo` for https logos only), so the client preview colours only itself. The admin app sends `X-Org-Id` on every admin call (`setAdminOrgGetter`), never on portal calls; switching org clears the query cache.
- **An onboarding has tabs, each its own address:** Overview (`/onboardings/:id`), Steps, Client preview (the real `PortalScreen` with a read-only session; works for drafts) and Links & follow-up.
- **A client never sees what the server doesn't send.** Do not filter internal steps in the UI as a security measure; the API already omits them. The UI must also not invent counts from data it doesn't have.
- **Links from templates are untrusted.** Only plain https goes into an `href` (`lib/links.ts`), always with `rel="noopener noreferrer"`. A bad one is shown as text, never as a link.
- **Server state lives in TanStack Query**, not component state. Errors show the server's own wording and every problem it listed (`ApiError.problems`), matched back to fields by label (`lib/problems.ts`).
- **Admin screens say what is wrong.** Any admin page that loads data shows `components/LoadError.tsx` on failure, never a bare "couldn't load" (and never an empty-state message when the real problem is an error). It names the setting to fix for a 401, the seed command with the user's own id for a 403, and the logs for a 500. The client portal is the opposite: its messages stay vague on purpose.
- **The step builder edits the same template document the server validates.** Steps and form questions carry builder-only `_uid` (a stable React key) and `_fresh` (added this session, so its key may follow its wording); `clean()` strips both before anything is sent. Keys of existing steps and questions never change in the builder, so saved answers keep matching. Drag and drop is `@dnd-kit` (pointer and keyboard), and every move also has ↑/↓ buttons. The builder sits inside other forms: it has no `<form>` of its own, every button is `type="button"`, and Enter in its fields doesn't submit. "Save as template" never adds a version to an existing template: a taken name is refused before saving.
- **A new step type needs a portal renderer** in `portal/steps/` registered in `registry.tsx`, a case in `admin/StepResponse.tsx`, and an entry in `builder/doc.ts` (`STEP_KINDS`) with a settings panel in `builder/ConfigEditor.tsx`. Unknown types render a safe fallback instead of crashing.
- **Uploads are checked on the device first** (`lib/uploads.ts` mirrors the server's allow-list, SVG excluded) and again by the server. The browser PUTs the file straight to the signed storage URL.
- **Phone first.** Touch targets are at least 44px, inputs use the right `type` and `inputmode`, and there is no horizontal scroll at 375px. Check new screens at that width.
- **Colour never carries meaning alone.** Every status is a glyph plus a word (`components/StatusBadge.tsx`), overdue says "Overdue", errors say what is wrong beside the field.
- **Tests:** Vitest with Testing Library. `test/helpers.tsx` has `mockFetch` (answers by `METHOD /path` and fails on anything unexpected) and `renderRoute` (with a fake portal session).

## Conventions

- Python: type hints, `from __future__ import annotations`, small modules, business rules in `services.py` (not in routers).
- TypeScript is strict about unused locals and params, uses `verbatimModuleSyntax` (use `import type`) and `erasableSyntaxOnly` (no enums or namespaces).
- Colour never carries meaning alone: every status ships with a glyph or a word.
- `node_modules/`, `.venv/`, `.env*` and `dist/` are git-ignored. Default branch is `main`.
